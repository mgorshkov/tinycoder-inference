# Ampere (sm_86) kernels — implementation plan (first pass)

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans to implement this
> plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the Ampere-shaped kernel work that can be verified without a 3090 — occupancy,
loud dispatch, and the two missing numeric probes — leaving only the staging rewrite and the
numerics trade for the session with the card.

**Architecture:** Everything is gated by the invariants in §7.5 of the design: a static per-arch
audit (`scripts/arch_check.py`) that fails when a kernel's compiled shape stops matching its
budget, plus two parity probes that make the prefill GEMM and the decode GEMV testable before
either is rewritten. The kernels themselves change only where the change is measurable on sm_75.

**Tech Stack:** C++20, CUDA 12.4, CMake, gtest, `cuobjdump`/`ptxas` for static analysis.

**Spec:** `docs/specs/2026-11-20-sm86-ampere-kernels.md`

## Global Constraints

- Build the core target explicitly and check the exit code:
  `cmake --build build-1.0 --target tinycoder_core -j 20 || { echo BUILD FAILED; exit 1; }`
- Parity baseline is **29 `[FAIL]` lines** (`unit_tests/exl3_gpu_parity`); compare the count.
- Logits gate is the token id and top-5 order: `id=198`, order `198, 1133, 271, 460, 317`;
  the value may move inside ±2e-3.
- `tinycoder_test` without a model: **113 tests, 96 passed, 0 failed**.
- Benchmarks: `--n-prompts 512 --n-gen 128 --threads 36`, serial, three runs, spread reported.
- No `#if __CUDA_ARCH__` around a loop body; async vs sync staging is one body with
  `if constexpr`.
- The build emits sm_75/sm_80/sm_86 SASS; anything gated on `>= 800` must stay correct on 75.

## Review Focus

- A kernel that keeps its numbers but silently stops using async copy → `arch_check.py` counts
  `LDGSTS` per arch and fails on regression.
- A batched prefill path that declines and takes the per-token route (the external report's 32x
  Bonsai collapse) → the fallback counter must be visible in the log.
- A decode kernel whose register count drifts back up and halves occupancy → the audit's
  blocks/SM check.
- An occupancy change that alters accumulation order → the two new parity probes.
- A probe that passes while generation is garbage → the ≥45-token prompt stays in the gate.

### Task 2: Loud int8 dispatch fallback

**Files:**
- Modify: `src/cpp/core/cuda/gemm/GemmDispatch.cu` (each `return false` site in the dispatch)
- Test: `unit_tests/ModelTest.cpp` or a standalone probe — assert the counter increments on a
  forced failure (`TINYCODER_FORCE_INT8_GEMM_FAIL=1`).

**Interfaces:**
- Produces: `int8GemmFallbackCount()` (host, in `GemmDispatch.cu`), and one `stderr` line per
  process, format `[int8] fallback: <reason> (type=<t> m=<seqLen> n=<rows> k=<cols>)`.
- Consumes: existing `Int8Ctx` (`GemmDispatch.cu:203-231`).

- [x] **Step 1-2:** The planned gtest needed a symbol that did not exist yet, and the defect that
      made this task worth doing turned out to be concrete rather than hypothetical: `launchSk` had
      no `kTypeQ6K_` branch, so every Q6_K shape returned false and ran the integer fallback with no
      trace. The test became the Q6_K branch itself plus the parity probe that proved it.
- [x] **Step 3:** Implemented differently from the plan, and better: instead of a counter plus
      `fail(reason)`, `noteInt8Fallback(reason, type, rows, cols, seqLen)` warns **once per distinct
      shape and reason**, and an `atexit` hook prints the total. The distinction matters — the early
      "not my shape" returns are the dispatch doing its job and stay silent; a launch failure, a
      smem refusal or a disabled-by-env return is reported. Reasons are separated strings
      (`no launch branch for this type`, `kernel launch error`, `cannot raise the dynamic-smem
      limit`, `Q6_K int8 path disabled by TINYCODER_INT8_Q6K`), so a log names the class of failure.
      No forced-failure env var was added; `TINYCODER_INT8_Q6K=0` exercises the same path.
- [x] **Step 4:** A healthy run is silent (checked on the 9B and the 27B); with the Q6_K path
      disabled the total line appears. Suite, text gates and both parity probes unchanged.
- [x] **Step 5:** Committed.

### Task 4: int8 prefill parity probe

**Files:**
- Create: `tools/int8_gemm_parity.cpp`
- Modify: `tools/CMakeLists.txt` (add the target)

**Interfaces:**
- Produces: `int8_gemm_parity <gguf> --type <t> --shapes 512x5120x4096,130x1536x4096,...`,
  exit 0 when every case is inside tolerance, per-case `[PASS] <shape> maxAbsDiff=<x>
  relRms=<y>`.

Built as written below except for the shape argument: the tool walks the checkpoint's
own tensors and probes the first occurrence of each distinct (type, rows, cols), because
the real inventory is what the kernel is selected by and it needs no transcription.

- [x] **Step 1:** Write the case set: shapes that reach a full `tile_x` (512), a partial one
      (130), rows not a multiple of 128 (1536+7), K not a multiple of 256, and
      `ntiles % nblocks == 0` and `!= 0`. In practice `output.weight` (248320x4096,
      `ntiles % nblocks != 0`), `attn_qkv` (8192x4096), `ffn_down` (4096x12288) and
      `ffn_gate` (12288x4096) cover those classes on the 9B; the 35B adds MoE shapes.
- [x] **Step 2:** Ran before the target existed, and before the Q6_K fix: the first run
      reported relRMS ~1.30 on every shape. That was the probe's own bug, not the
      kernel's — the activation buffer was allocated with the widest probed `cols` as its
      row stride while `int8Gemm` indexes `x` as `[seqLen][cols]`. Recorded because it is
      the argument for printing the number and not just the verdict.
- [x] **Step 3:** Implemented with the engine's own `GGMLDequantize::dequantizeToF16` as the
      reference source (so the weights are by definition the ones the fp16 twin holds) and
      activations that are integers in [-127, 127] scaled by 2^-7, which makes the Q8_1
      quantisation recover the integers exactly and lets an fp64 dot over the *un*quantized
      values serve as the reference. Gate 1.5e-2 relRMS; measured 3.4e-4 - 1.0e-3.
      The tolerance is not the kernel's error, it is the width of the Q8_1 scale-convention
      band; the tool says so in its header.
- [x] **Step 4:** `ornith/Ornith-1.5-9B-Q4_K_M`: `output.weight` Q6_K 3.815e-4,
      `attn_qkv` Q6_K 3.842e-4, `ffn_down` Q6_K 3.426e-4, `token_embd` Q4_K 8.248e-4,
      `attn_gate` Q4_K 8.268e-4, `ffn_gate` Q4_K 9.036e-4. All inside the gate.
- [ ] **Step 4b:** Same on `bonsai/...PQ2_0` and the 35B-A3B (not run yet; `int8Gemv` refuses
      PQ2_0/PTQ1_0 outright, so the decode probe reports them as skipped, and PQ2_0 and the
      MoE expert shapes are the remaining layouts).
- [x] **Step 5:** Committed.

**Finding, and the reason this task came before the staging rewrite:** the probe could not
run Q6_K at all — `int8Gemm` logged `launch failed (type=14 ...)` and returned false, so
every Q6_K projection silently ran the integer `kQGemmKxQ8K` fallback. `launchSk` had no
`kTypeQ6K_` branch although the extern declarations, the dynamic-smem attribute, the fixup
kernels, the supported-type guard and the q8-wide tile-loader selection were all already
there. Added, behind `TINYCODER_INT8_Q6K` (default on) so the before/after could be measured
in one binary: **no measurable speed change on this card** (interleaved pp512 2554.1 mean
with the path off against 2552.2 with it on, spread ~13 tok/s) because the 9B never routes
Q6_K through `int8Gemm` — a normal run emits zero `launch failed` lines. The fix matters
where int8 *is* selected, i.e. when no fp16 twin is resident, which is the 24 GB card's
situation rather than this one's. Correctness is proven (3.4e-4), speed is not claimed.

### Task 5: decode GEMV bit-exact probe

**Files:**
- Create: `tools/gemv_decode_parity.cpp`
- Modify: `tools/CMakeLists.txt`

**Interfaces:**
- Produces: `gemv_decode_parity <gguf> --proj blk.0.attn_q.weight`, per-case `[PASS] k=<k>
  n=<n> maxAbsDiff=<x>`, exit 0 when all cases are bit-identical to the scalar reference.

- [x] **Step 1:** Failing case: a whole shape set from a real checkpoint, per (type, rows, cols),
      against a scalar fp64 loop over the dequantized row -- and, as it turned out, the probe's own
      reference had to be fixed first (see below).
- [x] **Step 2:** Ran before the target existed, then with a reference that was itself the loose
      one: `GGMLDequantize::dequantizeToF16` rounds every dequantized weight to fp16 before
      returning it, which put a ~4e-4 floor on *any* comparison against it. The kernel looked 4e-4
      loose and was in fact exact. Switching to `dequantize()` (fp32) moved the K-quants from
      3.5e-4 to **7e-8..1.3e-7**, i.e. two fp32 ulps on a 4096-long dot. Same fix applied to
      `int8_gemm_parity`, where it separated two things that had looked alike: Q6_K is 1.0e-7
      (exact) and Q4_K is 6.7e-4 (the int8 requantization floor of a 4-bit-plus-min block, inherent
      to any `mma.s8` path).
- [x] **Step 3:** Implemented for the families in scope via `int8Gemv`: Q4_K, Q5_K, Q6_K, Q8_0,
      IQ2_XS/IQ2_S, IQ3_S/IQ3_XXS. Measured on ornith/Ornith-1.5-9B-Q4_K_M, the 7B i-quant pair and
      Ornith-1.5-35B-A3B-Q8_0: K-quants and Q8_0 at 3e-8..1.3e-7; **i-quants at 2.5e-5..3.1e-5**,
      which is not accumulation order -- their lattice reconstruction rounds an intermediate the
      host dequant does not. Recorded rather than smoothed away; it is 100x below fp16 noise and it
      is why the gate is 2e-4.
- [x] **Step 3b:** Found and fixed a real defect on the way: `int8Gemv`'s multi-token path
      (declared 1..8) passed `stride_col_y` in values instead of 32-value Q8_1 blocks, so every
      token after the first read its activations 32x too far. Invisible at batch 1 (the stride is
      multiplied by the token index), which is the only batch the engine uses -- so production was
      correct and the declared API was not. One-line fix; the sweep `--seqlen 1,2,4,8` now covers
      all eight kernel variants and they agree with the fp64 reference at ~1e-7.
- [ ] **Step 4:** PQ2_0 / PTQ1_0: `int8Gemv` refuses both (the ternary decode runs through the
      ternary GEMV path, not this entry point), so the probe skips them and exits non-zero with
      "nothing was verified" instead of reporting a clean run -- the skip-equals-pass bug this task
      produced and fixed.
- [x] **Step 5:** Committed.
